HLD · Caching

Wed 12 Nov, 19:0452 min activeCourse● Synced

ObjectiveUnderstand how a cache stays correct when more than one service writes the same data.

00:00
Topic

Cache-aside

00:04

The application checks the cache first, falls through to the database on a miss and populates the cache itself. Simple and robust, but the first request after an expiry always pays the full price.

00:11

Write-through writes cache and database together, so reads are always fresh but every write is slower. Write-back acknowledges from the cache and flushes later: fast, and you can lose data if the node dies first.

Understood“write-through writes cache and database together … write-back acknowledges from the cache”Clear and correct trade-off, in your own words.
00:19
Difficulty

I can’t see how invalidation stays correct when two services write the same key. Which one deletes the entry, and what if that message never arrives?

Missing conceptStill open: What happens to a cached entry when the primary write succeeds but the invalidation is lost?

Topic

Consistent hashing

00:34

Keys and nodes sit on a ring; a key belongs to the next node clockwise. Virtual nodes reduce the number of keys that move when a node joins.

Misconception“virtual nodes reduce the number of keys that move”They smooth the load across nodes. How few keys move comes from the ring itself.
00:46

LRU eviction: a hash map plus a doubly linked list, so get and put are O(1). Next: how LFU differs for skewed traffic.

What I learned

Cache-aside is the default. Write-back buys speed with durability risk. Consistent hashing bounds how much data moves on a topology change.
